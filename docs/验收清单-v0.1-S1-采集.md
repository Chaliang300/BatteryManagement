## 0. 先读这一段：本清单的性质与边界

1. **本清单是「怎么判」，不是「已经能」。** S0 未达出口，S1 未开工，本文不含任何实现承诺，
   也不改变 `AGENTS.md` §2 / §11 的阶段状态。
2. **证据分级沿用 S0 矩阵**：L0 代码检查 / L1 模拟测试 / L2 单元测试 / L3 实机测试 / L4 发布验证。
   本清单里凡写「本机可验」，意思是**该场景具备产出 L3 证据的硬件条件**，不是已经产出了。
3. **本轮盘点只证到「设备类存在 / 属性可枚举 / 服务已枚举」，没有读取任何电量值。**
   特别注意：Windows 把 GATT Battery Service（`0x180F`）枚举出来，**不等于**能读到 `0x2A19` Battery Level；
   后者必须由 S1 采集器实际连接读取才能确认，不许由 `0x180F` 存在反推。
4. **本机硬件有两条硬缺口**（详见 §4）：HID 0x06 电量设备为零、同型号第二台 BLE 设备为零。
   受影响场景在 §3 逐条标注「本机不可验 + 解除条件 + 责任人」，未标注不算验收通过。
5. 盘点纪律：全程只读（`Get-CimInstance` / `Get-PnpDevice(Property)` / `pnputil /enum-devices` /
   `HidP_GetCaps` 内存 P/Invoke），未配对或断开任何设备、未改系统设置、未写注册表。

## 1. 首读目标（1s / 3s / 10s）

`AGENTS.md` §3 P0-1 的口径：**本机电池 1s、HID 3s、BLE 10s**（冷启动，设备在已配对/在连接态）。

### 1.1 起止点定义（两种口径必须并列记录，不许只写数）

| 口径 | 起点 T0 | 终点 T1 | 用途 |
| --- | --- | --- | --- |
| **A. 外部口径**（不改产品代码即可测） | 调用 `Process.Start` **前一刻**的 `Stopwatch.Start()` | 进程日志出现该链路首条有效读数行 `firstValidReading` 的时间戳 | 早期冒烟；**含进程启动开销**，判据须放宽并在记录里单列，不得直接当首读指标 |
| **B. 进程内埋点口径**（**唯一引用口径**，S1 实现时落） | `Program.Main` 首行（`Stopwatch.GetTimestamp()` / `Environment.TickCount64`） | 该 provider 首条 **`Percent != null`** 的 `ReadingUpdated` 被 `DeviceStateService` 接收的时刻 | 判 1s/3s/10s 只用这个；不含窗口创建与首帧渲染 |

补充约定：
- 「有效读数」= 百分比非 `null` 的读数；发现设备、连接成功、读取失败、未知值**都不算**首读达成。
- 冷启动 = 进程刚起、设备处于已配对且在连接态；热启动（二次启动/窗口重开）单独记录，不与冷启动混算。
- 每轮记录必须附：`git rev-parse HEAD`、机型、构建类型（Debug/Release）、`dotnet --version`、轮次序号。
- 3 轮取**中位数**；任一轮超判据即判该项失败，不得取最好值。

### 1.2 可引用测量表达式（原样抄用）

```powershell
# 口径 A：外部，等待进程退出后再读日志时间戳
$sw=[Diagnostics.Stopwatch]::StartNew()
$p=[Diagnostics.Process]::Start($exe, '--diagnose-read', '20')
$p.WaitForExit()
$sw.Stop()
# 进程内埋点由 --diagnose-read 输出：firstReadMs（相对 Main 首行的毫秒数）
```

### 1.3 禁用表达式（`AGENTS.md` §15 新规的样板，原样保留）

同一 exe、同一台机器，只换表达式可差 **10–18 倍**——差的是工具不是程序。以下两条**禁止**用于性能/首读结论：

```powershell
# 禁用 A：测量无效。PowerShell 对 WinExe 的 `&` 不等待进程退出，测到的是「启动壳」。
#   S0 实测：28 ms（同机同 exe 的 --help 场景）
Measure-Command { & $exe --help }

# 禁用 B：不可作性能依据。Start-Process -Wait 自带约 0.96 s 工具开销。
#   S0 实测：1040 ms（同一场景），而真实进程耗时是冷 105 ms / 暖 56–60 ms
Measure-Command { Start-Process -FilePath $exe -ArgumentList '--help' -Wait -PassThru }
```

> 上述数字来自 S0 阶段（同一 exe、同一台机器、`--help` 立即退出，见
> `docs/验证记录-v0.1-S0-NET10工程基线.md` §2.4），本清单引用它是为了说明**表达式差异的量级**，
> 不是把 S0 的数字当 S1 首读基线。

### 1.4 判据

| 链路 | 判据（口径 B） | 证据 | 备注 |
| --- | --- | --- | --- |
| 本机电池（WMI） | `firstReadMs ≤ 1000` | `--diagnose-read` JSON + 日志 | 本机具备条件（§4） |

## 2. 稳定性（每链路连续 5 分钟）

对应 `AGENTS.md` §11 S1 出口「首发样机的三条链路各自 5 分钟稳定」。

### 2.1 采样与记录

- 用 `--diagnose-read 300` 输出**逐事件** JSON：`(utc, providerId, readingKey, percent, charging, kind, connection)`，
  `kind` 取 `Discovered / ConnectionChanged / ReadingUpdated / ReadingFailed / SourceUnavailable`。
- 判据**只读这份 JSON**，不靠肉眼看 UI；窗口/托盘的一致性另有 §3 的非本清单项。

### 2.2 判据（六条，缺一不可）

1. **有效读数次数**：60s 兜底模式下 ≥5 次；事件驱动链路（notify）≥10 次。
2. **失败计数**：连续失败 ≤2 次，且 5 分钟内累计失败 ≤3 次。
3. **空窗**：出现 >90s 未解释的读数空窗即判失败（过期判据按来源与刷新模式绑定，不许用 90s 统一判离线——判的是「空窗」不是「离线」）。
4. **抖动**：在线↔离线切换 ≤1 次；穿越抖动判失败。
5. **资源**：BLE 的 GATT 会话数不随采样增长；进程句柄数前后差 ≤10%（`Get-Process` 前后各取一次）。
6. **去重**：同一物理设备不产生第二条列表项（`DeviceKey` 稳定）。

### 2.3 失败与掉线口径（对齐 §5.6 / §6.7）

- 刷新暂停、锁屏、来源被禁用、任务取消**不计**设备读失败。
- 连续 3 次有效读取失败才判 **离线**；期间保留上次成功读数并标时效（「N 分钟前」），不显示 0%。
- 恢复后首条成功读数立即回**在线**并重置失败计数；不等待下一轮兜底。
- 单来源失败不影响其他来源的读数与新鲜度判定。

## 6. 执行边界与授权项

1. **适配器不可用（§3 #4）本轮与 S1 开工前都不做**：属系统状态变更，且 S1 未开工时测了也是空跑。
   留到 S1 执行阶段，由 Lead 逐个窗口批准，且必须：测完立刻恢复、记录恢复前后状态、**不许改注册表**。
2. **任何电量数值读取都不在本清单范围内**（本轮只读盘点未读取任何电量）。
3. 本清单不改变 S0 阶段状态，也不改变 `AGENTS.md` §2 / §11；S0 矩阵只保留 S0 出口判定，S1 判据以本文为准。
4. 证据落盘：每次首读/稳定性验收的 `--diagnose-read` JSON 与日志需按 commit 隔离存放
   （参照 qa-release 的证据根目录约定 `%LOCALAPPDATA%\Programs\PowerDock-qa\<commit7>\`）。
