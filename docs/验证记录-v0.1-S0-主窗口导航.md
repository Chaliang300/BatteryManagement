### 2.5 首帧性能（交错 A/B，含噪声地板对照）

**测量表达式原文**：`PowerDock.exe --diagnose-first-frame`；内部 `FirstFrameTimer`，
起点 = `Program.Main` 首行 `Arm()`，终点 = 首个 `CompositionTarget.Rendering`。
该口径**不含**进程创建与 CLR 启动前段（Windows 侧冷启动不在本口径内）。

| 组 | 样本 | 结果 |
| --- | --- | --- |
| 基线 `e99fea3` | 同会话交错 6 轮 | mean **355.8 ms**（352.8–360.4） |
| 本提交 `9568567` | 同会话交错 6 轮 | mean **379.7 ms**（374.4–383.6） |
| 增量 | — | **+23.9 ms（+6.7%）**，两组区间不重叠 |
| **A/A 噪声地板** | 同一产物复制成两目录各 6 轮 | 均值差 **5.9 ms**；但单次取值范围 356.0–421.2 ms |

结论：首帧增量约 **+24 ms**，超出 A/A 噪声地板，判为真实增量；该指标单次散布可达 ±30 ms、
跨会话还会整体漂移（同日另一会话两组同时抬高约 20 ms），**只能同会话同批对比，不能跨会话引用绝对值**。
379.7 ms 仍显著低于 AGENTS.md §12 的 `< 800 ms` 目标。

**根因与被证伪的假设**：原猜想是「构造期把四页全建了」，于是临时改成「首次切入才构造」并重测：
**379.7 ms → 378.1 ms，没有回收**。假设被证伪，试验改动已 `git checkout` 回退（产物保持冻结）。
即增量来自 Dock 四项带自定义模板的 `Button` 与新增内容树本身，而非页面构造次数。负面结论一并记录，
避免后人重复改一遍无收益的懒构造。

### 2.7 验证脚本自身的缺陷与修正（诚实记录）

这三条是本轮实测暴露的**验证脚本**问题，不是产品问题；写在这里是因为它们差点把环境问题记成产品缺陷。

1. **脚本以无 BOM 的 UTF-8 提交** → PowerShell 5.1 按 ANSI 解码中文注释，直接 `ParserError` 无法执行。
   已改为带 BOM 提交，并在文件头 `NOTES` 写明「编码 UTF-8(BOM) + LF」。
2. **输入通道探针窗口硬编码在 `(1900,60)`** → 换到较小屏幕后探针落到可视区外，
   `CH-01` 判失败并连带把鼠标结论降级为「未验证」。已改为按 `GetSystemMetrics(0/1)`
   实测屏幕计算探针尺寸与位置（留边距、贴右上角）。
3. **我曾加过「测量前用 `MoveWindow` 把主窗口摆进可视区」的步骤** → 该步骤让 UIA 取点产生
   `(-31496,-31155)` 这类溢出坐标，鼠标点击全部落到屏外。已**整段回退**；
   当前脚本不做窗口移动，窗口几何由产品自身的 `WindowStartupLocation.CenterScreen` 决定，脚本只如实记录。

另有一条**环境观测陷阱**：非 DPI-aware 的 PowerShell 进程用 `GetSystemMetrics` 会拿到虚拟化尺寸
（本轮实测为 1707×960/96DPI），而 DPI-aware 的验证脚本拿到的是真实值（2560×1440/144DPI = 150%）。
同一个机器上两个进程可能看到不同数字，**判 DPI 必须用 `GetDpiForWindow` 而不是 `GetSystemMetrics`**。

### 2.9 产物身份与「构建可复现」的边界（订正）

初次记录曾写「同一提交连续 3 次重建哈希一致，构建可复现」——**这个说法被后续实测证伪，特此订正**。

| 实测 | 结果 |
| --- | --- |
| 同一构建目录（`E:\project\BatteryManagement-dock-nav`）连续重建 2 次 | `DD5BC173…` / `DD5BC173…`，一致 |
| 同一目录 `clean` + 重建 | 仍 `DD5BC173…` |
| **另一全新 worktree**（同一提交 `a52a650`）`clean` + 重建 | **`6A8CB390…`，与上面不同** |
| 干净 worktree 内连续重建 2 次 + `clean` 重建 2 次 | 四次全为 `6A8CB390…` |

结论：`PowerDock.dll` 的字节**只对同一构建目录稳定**，跨目录会因构建路径被嵌入（PDB/资源路径）而不同，
字节数相同（142,848）。这**不是代码差异**。

据此调整：
- 本记录的被验产物哈希 `DD5BC173…` 只用于「同一目录内的前后对照」。
- 跨机器 / 跨目录复验请以**行为证据**（`--self-test` 项数、`--diagnose-dock-nav` 8 步、外部脚本 18 项）为准，
  **不要用 dll 哈希判「是不是同一份代码」**。
- 该陷阱已写入 `AGENTS.md §9`，避免后续复验再踩。

## 4. 哪些没验（不许省略）

1. **100% DPI**：本机只有 **1 台**显示器、`GetDpiForSystem=144`（150%），无 100% 会话可切。**未验证**——这是验收表里的必验项，因此本 PR 保持待复验状态，不做合并裁定。尝试过的全部手段与失败原因、以及给复验方的解除条件，见 `E:\project\_evidence\dock-nav\dpi100-attempt.md`（含 `SPI_SETLOGICALDPIOVERRIDE` 返回 True 但 DPI 不变、虚拟显示适配器当前无活动屏、改注册表需注销且属系统设置变更未执行）。
2. **标题栏拖动**：`DragMove()` 依赖真实鼠标拖拽与窗口消息；实现方合成输入在本机不可信（AGENTS.md §9），外部脚本本轮未覆盖该项。**未验证**。
3. ~~最小化按钮的真实鼠标点击~~ → **已部分验证**：`--diagnose-tray-restore` 已证实「最小化 → 托盘恢复」的**状态链路**（`IsIconic=true`、恢复 Normal、同一实例、状态保留），走的是真实 `DefaultWakeupMainWindow`。仍**未验证**的只剩「用鼠标点标题栏那颗最小化按钮」这一个动作本身（合成输入不可信）。
4. ~~从托盘恢复窗口~~ → **已验证（状态链路）**：`--diagnose-tray-restore` 3/3 轮通过。仍未验证的只剩「真实鼠标左键点托盘图标」这个输入动作。
5. **浅色主题下的 Dock 对比度**：主窗口当前只有深色底（`AppSettings.Theme` 默认 `dark`，仓库尚无 `ThemeService` 实现），本轮未引入主题切换。"保留深浅主题"在本轮只能判「未破坏既有行为」，浅色主题本身**未验证**（属 S2）。

7. **按下态视觉**：`IsPressed` 底色在「已聚焦」时被聚焦触发器覆盖（§2.7）。点击与切页不受影响，但按下反馈在外观上不可辨。**未验证 / 已知外观缺陷**。

9. **满盘 / ENOSPC 存储失败注入**：与本轮改动无关，沿用验收矩阵既有未验证子项。
