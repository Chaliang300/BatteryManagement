### 1.3 脚本

- `build.ps1`：`dotnet build PowerDock.sln`，支持 `-Configuration`、`-OutputDirectory`、`-NoRestore`，
  打印错误/警告计数与产物绝对路径，失败返回真实退出码。构建范围是解决方案级（Core + App + Tests），
  所以测试工程编译失败也会让构建失败，不会出现「源码能编、测试编不过」的假绿。
- `pack.ps1`：`dotnet publish -c Release -r win-x64 --self-contained true -p:PublishTrimmed=false -p:PublishSingleFile=true

  打印**发布耗时、单文件 exe 字节、解包后总字节与文件数、zip 字节、压缩比、exe/zip SHA256**，
  并把同样的度量写入 `dist\pack-report-<Version>-<Rid>.json`。
- `tools/dotnet-sdk.ps1`：SDK 探测（`PATH` → `DOTNET_ROOT` → `%ProgramFiles%\dotnet` → `%LOCALAPPDATA%\Microsoft\dotnet`
  → `%USERPROFILE%\.dotnet10` / `.dotnet`），不硬编码用户名；全部失败时打印中文安装指引并非零退出。

### 2.3 打包（D16 实际包体）

在下表所列提交上重跑 `pack.ps1`（依赖已还原）。下面这一段是 **@`46dd0bc`** 的输出原文；
在后续树 **@`612412d`** 上复测时（该树打包输入与 @`46dd0bc` 逐项相同，仅文档不同），exe 字节与解包后总字节完全不变，只有 zip 字节 `69,229,416 → 69,229,433`、
两个 SHA 变化（原因见下表）：

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\pack.ps1 -Version 0.1.0
 发布耗时        : 4.67s（第二次及以后；首次含 NuGet 还原为 14.13s，@612412d 复测 4.6s）
 压缩耗时        : 6.57s

 解包后总字节    : 173,075,134 字节（165.06 MB），3 个文件（PowerDock.exe + LICENSE + README.md）
 zip 字节数      : 69,229,416 字节（66.02 MB）
 压缩比          : 40.0%
 exe SHA256      : 311AF6AC8D80E8BC1DA429614988CA8BBC76AB49B774FC1EA1C3E583E0129A45
 zip SHA256      : 0F6FA7FF20C15E340948FAA55D833A3DA38442EC1479563A81DBB7B69C1EB02E
exit=0
```

**可复现证据只引字节数，且要区分「哪些字节数真的可复现」**：

| 证据 | 可复现？ | 原因 |
| --- | --- | --- |
| exe 字节 `173,072,004`、解包后总字节 `173,075,134` | **是** | 四次构建逐字节一致：@`1f6b6d3` 首批、@`46dd0bc` 重打、QA 独立复验 @`46dd0bc`、@`612412d` 复测 |
| zip 字节 `69,229,416`（@`46dd0bc`，本机与 QA 各一次）／`69,229,433`（中间树，+17 B）／`69,229,392`（@`612412d`，−24 B） | **否（只能引量级 66.02 MB）** | zip 压缩的对象是 exe，而 exe 内嵌 `ProductVersion = 0.1.0+<构建时 commit>`；换 HEAD 后 deflate 输出相差 ±17 B |
| exe SHA256 | **否** | 同上的 `ProductVersion` 随构建时 git 状态变化，换 HEAD 构建即换哈希 |
| zip SHA256 | **否** | `Compress-Archive` 把打包时刻写进 zip 头，且叠加上述内容差异，每次打包都不同 |

> 这一条在订正过程中**被自己的复测推翻过一次**：原本打算把 zip 字节也列为可复现，
> 在后续两次重打中分别得到 `69,229,433`（比 @`46dd0bc` 多 17 B）与 `69,229,392`（@`612412d`，比 @`46dd0bc` 少 24 B）。**三次打包三个值，zip 字节是量级证据而不是可复现证据。**
> 引用包体时请只写：**exe 173,072,004 B（165.05 MB）/ 解包后 173,075,134 B / zip 约 69.2 MB（66.02 MB）**。

**订正说明（上一版 3 个数字错在哪，已核实根因）**：上一版记的是 `解包后 173,073,733 / zip 69,228,651 / exe SHA 4625FEBB…`。
算术 `173,073,733 − 173,072,004 − 1,068 = 661`，即那次打包隐含 **README = 661 B**；
而提交版 README = **2,062 B**（`git cat-file -s origin/main:README.md` = 661，当前树 = 2,062，差 1,401 B）。
两次打包的 exe 字节完全相同（173,072,004），差异只来自随包复制的 README 新旧 ——
那次测量发生在**同一 PR 内重写 README 之前**。这是「记录与最终树不一致」，不是构建/打包问题；本次已在最终树上重跑并回填。

结论：**未裁剪自包含单文件成立**——发布目录里没有并排的 DLL，WPF 原生库被收进 exe。
包体代价为 exe 165 MB / zip 66 MB（对照 .NET Framework 基线 zip 32,561 B），这是 D16 明确的取舍；
可接受上限仍待确认（见第 3 节）。降低体积的可用杠杆 `EnableCompressionInSingleFile=true` 本轮未开启，保持基线原样。

### 2.4 单文件解包行为与 `--help` 退出耗时（**非首帧**）

**先声明口径**：本节测的是 `PowerDock.exe --help` 从进程创建到退出的耗时，包含 .NET 运行时启动与
单文件原生库解包，**不含窗口创建与首帧渲染**，不能当「启动性能 / 首帧」指标引用。
同一 exe、同一台机器，换一个测量表达式能差 10–18 倍，所以数字必须带表达式：

| 测量表达式（PowerShell 原文） | 冷启动（测量前删 `%TEMP%\.net\PowerDock`） | 预热后 3 次 | 说明 |
| --- | --- | --- | --- |
| `$sw=[Diagnostics.Stopwatch]::StartNew(); $p=[Diagnostics.Process]::Start($exe,'--help'); $p.WaitForExit(); $sw.Stop()` | **105 ms** | **57 / 60 / 56 ms** | 进程真实耗时，**对外只引这一行** |
| `Measure-Command { Start-Process -FilePath $exe -ArgumentList '--help' -Wait -PassThru }` | 1040 ms | 1030 / 1034 / 1040 ms | 含约 0.95–0.97 s 的 `Start-Process -Wait` 自身开销，**不可作性能依据** |
| `Measure-Command { & $exe --help }` | 28 ms | 18 / 20 / 21 ms | PowerShell 不等 WinExe，`&` 立即返回，**测量无效** |

订正说明：上一版记录写「冷 109 ms / 暖 57、68、58 ms」，数字本身是表达式 1 的实测，但记录没写表达式；
QA 复验用表达式 2 得到「冷 1048 / 暖 1039、1042、1045 ms」，两个数都真实，差的是工具开销不是程序。
本条改为「表达式 + 数字」双列，并明确表达式 1 为唯一引用口径。

解包事实（D16 要求）：首次运行前后对比 `%TEMP%\.net`：

```
运行前：%TEMP%\.net 不存在
运行后：%TEMP%\.net\PowerDock\RIxR2pUcpgfL\  共 5 个文件 / 8,215,952 字节
        D3DCompiler_47_cor3.dll        4,741,488
        wpfgfx_cor3.dll                1,956,648
        PresentationNative_cor3.dll    1,235,240
        PenImc_cor3.dll                  158,032
        vcruntime140_cor3.dll            124,544
```

真正成立的结论（两种表达式下都成立）：**解包是一次性的**，不是每次启动都解包。

- 表达式 1：冷 105 ms vs 暖 56–60 ms，差 45–49 ms，与 8.2 MB 解包量级相符；
- 表达式 2：冷 1040 ms vs 暖 1030–1040 ms，差值落在噪声内（被 0.96 s 工具开销掩盖），
  因此它只能证明「冷热无数量级差异」，不能用来量化解包代价。

`%TEMP%` 不可写的受限环境需要单独验证（见第 3 节）。

## 3. 已知缺陷与哪些没验

### 3.1 已知缺陷（`46dd0bc` 上仍然存在，**本 PR 不修**）

PR #1 是**纯迁移**：只换运行时、工程文件与脚本，不重写功能逻辑。因此下面三条缺陷在本 PR 前后完全一致，
修它们会改变行为、让迁移复验失效。**归属：PR-S0-03 / PR-S0-04 / PR-S0-05，不在本 PR 范围。**

| # | 缺陷 | 证据（`46dd0bc` 上的行号） | 后果 |
| --- | --- | --- | --- |
| K1 | 单实例自检是**同进程**自测：MUTEX-01 在同一个测试进程里 `new SingleInstanceService(...)` 两次（`:272`/`:276`/`:283`），PIPE-01 的服务端与客户端也在同一进程（`:334`/`:342`） | `src/PowerDock.App/Diagnostics/SelfTestRunner.cs` | 通过只能说明「Mutex 名称与管道代码路径可执行」，**不能外推真实二次启动、跨进程管道通信与置前** |

写在这里是防止后来人误以为「迁移时顺手修好了」——**没有修，一行都没动**。

### 3.2 哪些没验

1. **「无 SDK 的目标机可启动」只验了一半**：本机 PATH 上的 `dotnet` 确实没有 SDK，脚本靠探测绕过了它；
   但机器里装着 SDK。脚本侧的失败路径本 PR 只做构造性验证，真实「干净机无 SDK」由 QA 独立复验补强
   （`buildfail-A-nodotnet.txt` / `buildfail-B-runtimeonly.txt`，13 条断言），**不计入本 PR 实测**。
2. **托盘与窗口只验了自检内部结论，没有人眼可视确认**：TRAY-01/02、WIN-01 由自检内部渲染与句柄检查判定为通过，
   但任务栏溢出区、浅色任务栏反色、真实首帧、Acrylic 材质均未截图取证；K2 说明托盘结论本身不可信。
3. **并发二启与置前拒绝未复验**：属 S0 退出条件，需要多进程与真实前台交互；K1 说明自检项不能替代它。
4. **DPI / 多显示器 / 窗口位置校正未验**：旧的 `AppContextSwitchOverrides`（`DoNotScaleForDpiChanges=false`）未延续，
   .NET Core+ WPF 默认 Per-Monitor DPI，行为差异需实际拖动窗口与切换缩放比例确认。
5. **包体上限未决**：165 MB exe / 66 MB zip 只是实测值，D16 的「可接受上限」仍需产品侧确认；
   若上限更严，可选项是 `EnableCompressionInSingleFile`（体积降、启动解压增）或重新评审运行时。
6. **受限 TEMP 环境未验**：单文件解包依赖 `%TEMP%` 可写；企业策略禁用 TEMP 执行的情形未测。
7. **跨 Windows 版本未验**：仅在本机 Windows 11 Build 26220 验证；Windows 10 与低于 22621 的 Build 下
   Acrylic/圆角降级行为未测。
8. **`dotnet test` 只在本机 SDK 下跑过**；UI 生命周期相关代码（托盘、窗口、单实例）没有自动化测试覆盖，
   它们只有 `--self-test` 这一条路径，而该路径受 K1/K2 限制。
