## 一、做了什么

1. **单实例协议 v2（`src/PowerDock.App/Shell/SingleInstanceService.cs`，重写）**
   - 命名对象按 **用户 + 会话** 隔离：`Local\PowerDock_Mutex_<session>_<userSid>`、`PowerDock_Pipe_<session>_<userSid>`、`Local\PowerDock_Ready_<session>_<userSid>`；不再使用 `ASFW_ANY`（保留常量以防误用，但代码路径已删除调用）。
   - 主实例所有权判定：`new Mutex(false, name)` + `WaitOne(0)` 验所有权（不再依赖 `createdNew`）。
   - **就绪握手**：主实例先创建 readiness event，管道服务端真正开始 `BeginWaitForConnection` 后才 `Set()` 并记录 `Primary instance ready (pipe listening)`；二启等待该事件，区分**无主（20）/ 主未就绪（21）**。
   - **客户端 SID 精确校验**：`GetNamedPipeClientProcessId → OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) → OpenProcessToken(TOKEN_QUERY) → GetTokenInformation(TokenUser) → ConvertSidToStringSid`，与当前用户 SID 比较；任一步失败=拒绝，并把具体原因/win32 码写入日志；删除旧的 `GetImpersonationUserName().IndexOf(UserName)` + 异常全放行。
   - **定向授权**：二启通过 `GetNamedPipeServerProcessId` 取得主实例 PID，再 `AllowSetForegroundWindow(primaryPid)`，日志 `Foreground authorization: AllowSetForegroundWindow(<pid>) returned <True|False>, win32=<code>`；主实例侧日志 `Foreground activation: SetForegroundWindow returned <True|False>`，两条分开记录，使“授权失败”与“目标无响应”可区分。
   - **有界应答**：服务端/客户端 read/write 均带超时（2.5s 协议、1s 写、1.5s 就绪/连接），监听循环 250ms 轮询 `_stopEvent`，单个不说话客户端不再卡死后续二启；`PipeSecurity` DACL 保留作纵深，降级时记录原因。
   - **退出码契约**（`SingleInstanceExitCodes`，写入 `--help`）：`0` 成功 / `20` 无主实例 / `21` 主未就绪 / `22` 置前被拒 / `23` 身份被拒 / `24` 协议超时。
   - 二启失败时 Program 显示**可自动关闭（4s）的可读提示**（22 除外：主实例任务栏闪烁即反馈）；`--no-feedback` 供自动化关闭提示。
2. **`src/PowerDock.App/Program.cs`**：接入新协议与退出码；`--help` 增加退出码表、`--autostart`、`--no-feedback`；失败提示与 4s 看门狗自动关闭。
3. **`src/PowerDock.App/Interop/NativeMethods.cs`**：新增 `GetNamedPipeClient/ServerProcessId`、`OpenProcess`、`OpenProcessToken`、`GetTokenInformation`、`ConvertSidToStringSid`、`LocalFree`、`TryGetProcessUserSid`、`MessageBox/FindWindow/PostMessage`。
4. **`src/PowerDock.App/Diagnostics/SelfTestRunner.cs`**：`MUTEX-01` / `PIPE-01` 改为**独立线程**持锁/起服务端（避免同线程 Mutex 递归误判为“主实例”），校验名称含 `_<session>_`、二启退出码为 0；其余 12 项不动。
5. **`tools/verify-single-instance.ps1`（1030 行，随本 PR 提交）**：真实多进程门禁；本次同步更新 C1 日志顺序断言（`mutex < activate < foreground`、`activate < response`），二启统一带 `--no-feedback`。

## 六、分支属主复核（shell-ui，独立于 600f5be 提交人）

- 复核范围：`600f5be` 相对 `9693c45` 的 delta（`SingleInstanceService.cs`、`tools/verify-single-instance.ps1`、本文档）。
- 复核结论（逐行）：
  - `ConnectWaitMs = ProtocolTimeoutMs + 1000 = 3500ms`，大于服务端丢弃静默客户端的 2500ms 协议超时，能覆盖"主忙"窗口；
  - 两处 `[case=NO_PRIMARY]` 只位于"就绪事件不存在/打开失败"分支，符合"20 只给无主"的契约；
  - 连接超时分支返回 `PrimaryNotReady(21)` 且日志含 `[case=PRIMARY_BUSY]`，与 `20` 可区分；
  - 身份拒绝日志带 `[case=IDENTITY_REJECTED]`，不与前两者混用；
  - C7 断言"绝不 exit=20"、主实例存活、日志不含 `case=NO_PRIMARY`；补充复核意见见下。
- **复核发现（1 条，不阻塞代码修正，需门禁侧确认）**：C7 断言 `exit ∈ {21,22}`，但在**解锁桌面**下，连接窗口（3500ms）大于服务端丢弃静默客户端的 2500ms，二启通常会**恢复并成功置前（exit=0）**；此时 C7 会误判失败。建议将断言放宽为 `exit ∈ {0,21,22}`（仍保持"绝不 20"的核心判据），或把"C7 期望 21"改成"主忙期间不得 20，恢复后允许 0/22"。本项已报 Lead。**Lead 裁决（采纳）**：C7 的 `exit` 断言放宽为 `{0, 21, 22}`；核心判据不变——**绝不出现 `exit=20`**、主实例存活、日志无 `case=NO_PRIMARY`。本次修改见 `tools/verify-single-instance.ps1` 的 C7 用例。
**现象（修复前实测）**：一个不说话（silent）客户端占住管道时，下一次**正常**二启在 **1,584 ms 以 `exit=20`（无主实例）** 退出，而主实例仍在运行（2.5 s 后才丢弃该静默客户端）。
用户看到的是「没有主实例」，事实是「主实例忙」——与刚修掉的「零实例静默失败」是同一类错误的镜像。

**根因**：`ConnectWaitMs = 1500` **小于**服务端 `ProtocolTimeoutMs = 2500`。二启在服务端丢弃静默客户端之前就放弃连接，且该分支复用了 `NoPrimary(20)`。

**改动**（`src/PowerDock.App/Shell/SingleInstanceService.cs` + `tools/verify-single-instance.ps1`）：
1. `ConnectWaitMs = ProtocolTimeoutMs + 1000`（1500 → **3500 ms**），确保不会在服务端还没丢完静默客户端时判失败；
2. 连接超时分支由 `NoPrimary(20)` 改为 **`PrimaryNotReady(21)`**；`20` 只保留给「就绪事件确实不存在」的场景；
3. 日志可区分三类：`[case=NO_PRIMARY]`（就绪事件不存在）/ `[case=PRIMARY_BUSY]`（就绪事件存在但连接未接受）/ `[case=IDENTITY_REJECTED]`（身份校验拒绝）；
4. `tools/verify-single-instance.ps1` 新增 **C7**：静默客户端占位 → 正常二启 → 断言 **绝不出现 `exit=20`**、`exit ∈ {21,22}`、主实例仍存活、日志不出现 `case=NO_PRIMARY`。

**修复后实测（锁屏会话，前台无关断言语义）**：
- T1 正常二启：`exit=22`（锁屏下置前被拒，符合预期）；
- T2 静默客户端占位后正常二启：**`exit=22` / 2,210 ms**（在 3500 ms 窗口内等到服务端丢弃静默客户端后成功连上，不再误报 20），主实例存活 1；
- T3 零实例（探针持 Mutex 无管道）：**`exit=20`**，日志含 `case=NO_PRIMARY`（语义未被破坏）；
- `dotnet test` 12/12 通过、`--self-test` 14/14 通过、`build.ps1` 0 错误 0 警告；结束时 0 进程 0 管道。
- 说明：`21`/`PRIMARY_BUSY` 属**兜底**路径——3500 ms > 2500 ms，单静默客户端场景总能恢复，实际触发需要连续排队的多个静默客户端；其正确性为代码级（L0）证据，尚无实机触发记录。



- **补充（非门禁实机证据）**：`21`（主忙/未就绪）兜底路径已由非门禁探针 `tools/verify-single-instance-stress.ps1` 用 `NtSuspendProcess` 冻结主实例实机触发：`exit=21`、`3578ms`、日志含 `[case=PRIMARY_BUSY]`、`gating=false`（不参与门禁判定，红不算产品失败）。证据：`%LOCALAPPDATA%\Programs\PowerDock-qa\9693c45\stress-evidence\`（qa-release 实跑 14/14）。
